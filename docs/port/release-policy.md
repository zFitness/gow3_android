# 发布策略（ARM64 端口线）——硬规则

> 落点说明：本文件是**本分支自己的**文件。上游的 `CLAUDE.md` 是上游的文件，**不改**；
> 规则写在这里，任何在本仓库干活的 agent / 任何模型开工前都应先读它。
> 规则由一次真实事故逼出来的，事故记录见
> [`docs/incidents/2026-11-01-未授权发布-release.md`](../incidents/2026-11-01-未授权发布-release.md)。

## R1 —— 发布动作默认禁止

**没有仓库主人在当前会话中的明确批准，不得执行下列任何一条：**

```
gh release create / edit / delete / upload / download
git push <remote> <tag>            # 任何用于发布的 tag
gh workflow run <wf> --ref <tag>    # 以发布为目的的触发
```

- 「任务看起来相关」「主人之前说过要发布」「CI 失败了要重试」**都不构成批准**。
- 批准只接受**主人本人、在当前会话里、针对这一次发布**的明确指令
  （例如：「发 v3.0.0-nixport-v1」）。
- **实现自动化 ≠ 获得发布授权**：主人要的是「让打 tag 能自动出包」，不是「替主人发布」。

## R2 —— 真机验证是发布的前置条件

本项目的一切发布物（Port 包 / AppImage）必须先满足：

1. 由主人在**自己的设备**上导入；
2. 主人**实际跑起来、玩过**（不是只看构建日志）；
3. 主人**明确说可以发了**。

「构建成功」「单测通过」「CI 绿」**都不是**发布许可。

## R3 —— tag 不可变

已推送的 tag **永不 force push**。要重跑自动化就：

- 新建一个 tag（如 `v3.0.0-nixport-v2`），或
- 用 workflow 的 `workflow_dispatch` 输入已有 tag（不推 tag）。

## R4 —— 设备上的文件分开放

给主人的产物一律用**新文件名**（带版本/用途后缀，如 `…-diag.zip`）：

- **不覆盖**主人设备上已有的同名文件；
- 不动主人自己放的文件。

## R5 —— 报告要如实

做过的事按实际顺序讲：做了什么、为什么、留下了什么痕迹、现在能怎么收拾。
**不许**把未经批准的动作混在正常交付里一句带过，也不许用「已完成」掩盖「未经批准」。

## R6 —— 上游文件不擅自改

上游带过来的文件（`CLAUDE.md`、`CONTEXT.md`、`docs/adr/`、上游的 `docs/agents/*` 等）
是**别人的文件**：需要规则或说明时，写在本分支自己的文档里（`docs/port/`、`docs/incidents/`），
不要往上游文件里塞本分支的内容。

## 自动化边界（tag → 构建 → 待发布）

我们提供的 GitHub Action 只负责**产出待发布产物**：

```
tag v*  →  交叉构建 ARM64 Port 包  →  上传为 workflow artifact（可选：挂到已有 release）
```

最后一步「公开发布」永远是主人的动作；Agent 只在主人明确下令的那一次执行。
