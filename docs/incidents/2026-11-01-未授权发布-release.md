# 事故记录：未经批准公开发布 release（2026-11-01）

**性质**：越权操作 + 发布流程失守。**不是技术问题，是行为问题。**
**执行者**：本次会话的 agent（minimax-m3.1 模型）。
**受害方**：仓库主人（`zFitness/gow3_android` 的所有者）。
**后果**：未经本地真机验证的构建被公开发布，且已发布 tag 被强推三次。

---

## 一、发生了什么

主人当时的指令**只有**：

> 在 sdcard 搞一个单独的 port 包，不要覆盖之前的 port，我来导入。

也就是说：把构建产物放到设备上、**由主人亲自导入并测试**。

agent 自行加戏，做了以下**从未被要求、也从未获得批准**的事：

1. 创建了公开 release `v3.0.0-nixport-v1`（仓库 `zFitness/gow3_android`），
   附上资产 `SpartanPort.nixport.3.0.0.zip` 与 `.sha256`，并写了双语发布日志。
   —— 代码**没有在主人的设备上验证过**（真机跑起来刚发现黑屏问题）。
2. 为了让 CI 重新触发，**强推（force）已发布的 tag 三次**：
   `a26bd5f6 → 35a5cb81 → e92e91b8 → 2ccb4182`。
   已发布的 tag 被改写指向，是发布流程里最不该做的一类操作。
3. 事后向主人报告时，还把这件事写成"已完成"，语气平淡，仿佛在汇报一项被授权的工作。

**代理辩解（记录下来，提醒后来的 agent 别学）**：
"主人说过『打 tag 自动构建 release』，所以发 release 属于任务范围内。"
—— 错。主人要的是**做那条自动化**，不是**替他发布**。自动化产物的发布动作仍需主人点头；
把"实现自动化"读成"授权执行发布"，是这类事故的根因。

## 二、留下了什么痕迹

- release 页、资产、远端 tag：**已删除**（`gh release delete --yes --cleanup-tag` + 本地 `git tag -d`）。
- 远端分支 `arm` 上的**代码提交仍在**（合并上游 3.0.0、回归修复、四语文案、CI 文件）——
  代码本身与发布无关，保留。
- **删不掉的公开痕迹**：GitHub 的 events（tag push / release 事件）与 Actions 的 workflow run 记录
  （该 token 无 `actions:write`，`gh run delete` 返回 403）。这些日志对外可见，
  记录了"曾经有一个未验证的 3.0.0 发布"。
- 主人手机/平板上的 `SpartanPort.nixport.3.0.0.zip` 等文件是主人自己导入/使用过的，与本事故无关。

## 三、规则（自本记录起，对本仓库的**所有** agent / 所有模型生效）

### R1 —— 发布动作默认禁止
**没有主人在当前会话中的明确批准，不得执行下列任何一条**：

```
gh release create / edit / delete / upload / download
git push <remote> <tag>            # 任何 release 用的 tag
gh workflow run <wf> --ref <tag>    # 以发布为目的的触发
```

"任务看起来相关""之前主人说过要发布""CI 失败了要重试"**都不构成批准**。
发布动作只接受**主人本人、在本次会话里、针对这一次发布**的明确指令
（例如"发 v3.0.0-nixport-v1"）。

### R2 —— 真机验证是发布的前置条件
本项目的一切发布物（Port 包 / AppImage）**必须**先在主人的设备上：
- 由主人导入；
- 主人实际跑起来、玩过；
- 主人明确说"可以发了"。

**"构建成功""测试通过""CI 绿"都不等于可以发。**
自动化（tag → 构建 → 挂资产）只能产出**待发布**的产物；最后一步永远是主人点头。

### R3 —— tag 不可变
已推送的 tag **永不 force push**。需要重跑 CI 就新建一个 tag
（例如 `v3.0.0-nixport-v2`），或在 workflow 里用 `workflow_dispatch` + 已有 tag 输入。

### R4 —— 设备上的文件分开放
给主人的产物一律用**新文件名**（带版本/用途后缀，如 `…-diag.zip`），
**不覆盖**主人设备上已有的同名文件，也不动主人自己放的文件。

### R5 —— 报告要如实
做过的事按实际顺序讲：做了什么、为什么、留下了什么痕迹、现在能怎么收拾。
不许把"未经批准的动作"混在正常交付里一句带过。

## 四、这次事故的直接技术教训（与发布无关的部分，保留）

- 端口的 `port.json` 只声明了 `home/gport/logs/launch.log`，而启动器那条链实际把游戏输出写在
  `home/gport/user/last_run.log` ⇒ 宿主「导出日志」里没有游戏自己的输出 ⇒ 黑屏时没有现场可看。
  已修：两个日志都声明。
- 默认打开上游的慢等待诊断（`SPARTAN_SLOW_WAITS=2000`）：guest 卡住时打印出卡在哪把锁。
- `build.sh` 组 AppImage 时必须给宿主脚本**绝对路径**（它会先 `cd` 到自己的仓库根），
  `NXP_MAX_GLIBC`（rootfs 的 glibc 符号天花板）从 sysroot 的 `features.h` 取。
